# Daily Report (日报总结)

把当天**真正落地的改动**，用**非程序员也看得懂**的大白话说清楚，按周归档到指定目录。

## 日报存储位置

- 目录：优先使用用户本次明确指定的路径；其次读取环境变量 `DAILY_REPORT_DIR`。
- 每周一个文件，文件名 = `日报-<本周周一>至<本周周日>.md`
  - 例：`日报-2026-09-14至09-20.md`
  - 跨月时省略重复年份，例：`日报-2026-09-28至10-04.md`

若用户没有指定目录且环境变量为空，先询问希望保存到哪里，收到路径后再写日报。不要把个人路径写回本技能文件；用户本次指定的目录在本次任务中使用。

## 文件结构

新建周文件时先写标题，再把每天的内容按日期先后追加到末尾：

```markdown
# 2026-09-14 至 2026-09-20 日报

## 2026-09-15
- 修好了切换页面后摄像头偶尔不关闭、需要重启软件的问题
- 退货单导入更严谨了：上传的文件里如果有重复或填错的单号，会整批拒绝，不会只导入一半

## 2026-09-16
- 新增了发货单批量导出 Excel 的功能
```

- 同一天的内容统一放在该日期的 `## YYYY-MM-DD` 标题下
- 新的一天追加到文件末尾，保持时间从早到晚
- 同一件事只写一条，不要重复记录

## 写什么

只记录**确实改动了代码、配置或文档**的成果：新增的功能、改好的问题、调整过的做法。

每条用一句话讲清楚三件事：**谁**（哪个页面 / 哪个角色）、**做了什么**、**得到什么结果**。

- 新增了……
- 修好了……（原来会怎样，现在不会了）
- 调整了……（以前是怎样，现在改成怎样）
- 把……改成了……，以后……更方便 / 更安全 / 更省事

## 不写什么

- **不写技术细节**：文件名、函数名、类名、接口地址、字段名、表名、端口号、框架 / 技术栈名称，一律不出现
- **不写过程**：排查过程、根因分析、方案讨论、代码审查结论、只读调研，都不记录
- **不写没落地的内容**：只是聊过、想过、规划过，但没真正动手改的，不记录
- **不写空话**：不写"优化了性能""提升了体验"这类没有具体内容的说法

## 语言对照示例

| ❌ 太技术、太细 | ✅ 大白话 |
| --- | --- |
| 优化 InvtRefund.php import_file 校验逻辑，新增表头运单号去重校验 | 退货单导入更严谨了：文件里如果有重复或填错的单号，会整批拒绝，不会只导入一半 |
| 修复 webSdkCleanup.ts 全局清理锁，修复 stopCameraPreview 回调式调用 | 修好了切换页面后摄像头偶尔不关闭、需要重启软件的问题 |
| 抽取 useWebSdkCamera composable 封装 SDK 生命周期，消除 290 行重复代码 | 把三个页面里重复的摄像头代码合并成一套，以后改一处三处都生效 |
| 分析分类规则未闭环问题，输出设计文档说明现状 | （属于调研分析，不记录） |

## 工作流程

1. **确定目录**：依次使用用户本次指定的目录、环境变量 `DAILY_REPORT_DIR`；两者均无值时先询问。不要修改本技能文件来保存配置。
2. **确定周文件**：算出本周周一和周日，拼出文件名，检查目录下是否已存在；不存在就新建并写入标题。
3. **检查当天记录**：在周文件里找当天的 `## YYYY-MM-DD` 段落。
4. **整理内容**：从本轮对话里挑出真正落地的改动，按「写什么 / 不写什么」转成大白话，一般 2～5 条，每条不超过约 40 字。
5. **写入**：
   - 当天没有段落 → 在文件末尾新增日期段落，写入条目
   - 当天已有段落 → 只把新条目补到该段落末尾，已有条目不动、不重复
   - 补记其他日期 → 写入那个日期所属的周文件
6. **如果没有任何可记录的改动**（只讨论、只问答、只排查）：告诉用户今天没有实际改动，不需要写入，不要硬凑内容。

## 注意事项

- 新内容一律追加，绝不覆盖或重写已有内容
- 日期格式严格使用 `YYYY-MM-DD`，文件保存为 UTF-8
- 写入前自检一遍：读起来像不像给不懂技术的人看的？有没有出现文件名 / 技术名词？有没有把"排查 / 讨论"当成果写进去？
