# 编写与维护

## 将文档或需求整理为技能

用户提供文档、需求、操作记录或项目经验时，按以下流程整理。

1. **判断是否值得复用**：识别重复出现的任务、规范、决策方法或操作流程。仅有一次性目标而没有可复用方法时，说明判断，按原任务需要处理，不为凑目录创建技能。
2. **检查已有技能**：先查看 README、catalog.yaml 和相关技能的 SKILL.md。属于已有能力的补充就合并；触发场景和工作流程确实独立时再新建。若材料自然覆盖多个独立能力，可按实际用途拆分。
3. **提炼技能入口**：写清何时使用、必要输入、关键步骤、预期输出和适用边界。区分已确认的规则与待澄清事项；不把单次业务细节、偶发失败或个人偏好写成普遍要求。影响执行的关键信息缺失时先询问，其他细节可做合理假设并注明。
4. **按需安排资料**：核心流程放 SKILL.md；详细规范放 references/；可复用模板放 assets/ 或已有的 templates/；只有确有重复执行或可靠性需求时才添加 scripts/。不要直接把整篇文档堆入入口，也不用提前创建空目录。
5. **保留来源与适用条件**：在相关参考文件中注明来源链接或文档名称、版本或日期；来源较多时再设 sources.md。保留适用的来源与许可说明，移除密钥和无关的个人、业务信息。本机路径改成用户输入或配置。对依赖版本、工具或环境的内容说明条件；未核实的信息不要写成已验证事实。
6. **验证并登记**：补一个典型使用示例，写明输入与预期结果；按可用环境验证相关行为。涉及真实数据写入、发送或发布时，在用户授权范围内进行，必要时使用隔离示例。明确哪些已验证、哪些受环境限制未验证。新增技能登记为 experimental，并同步 catalog.yaml 与 README；已有技能按实际变化更新。

例如，“给订单页增加导出按钮”是一次具体任务；“按项目约定实现列表导出，处理权限、大数据量和异常”才可能提炼为可复用能力。订单字段和本次页面信息应保留为示例或输入，而非所有项目都必须遵守的规则。

可以直接向 AI 提出：

> 把这份文档或需求整理成技能。先判断是否适合复用，并检查是否应合并到现有技能；保留必要参考资料和来源，补充使用示例与验证结果，更新仓库索引和导航。若材料只是一次性任务，说明理由，不强行创建技能。

## 添加技能

1. 在 skills/ 下建立英文小写短横线命名的目录，名称不超过 64 个字符。
2. 编写 SKILL.md，YAML frontmatter 至少包含 name 和 description，name 与目录名一致。
3. 在 catalog.yaml 的 skills 下加入分类、标签、状态、平台和一个真实使用示例。
4. 按需添加 scripts/、references/、assets/、examples/；没有用途的目录不用建。
5. 在 README 对应分类中添加技能链接和简要用途，检查文件引用，再用典型任务验证行为。

最小入口：

```markdown
---
name: example-skill
description: 说明实际能力，以及什么时候应该使用。
---

# 技能名称

说明需要的输入、完成任务的流程、输出和必要约束。
```

## 索引字段

| 字段 | 作用 |
| --- | --- |
| category | 一个主场景，首页按它分组 |
| tags | 多个检索关键词，可中英混合 |
| status | experimental / stable / deprecated |
| platforms | windows / macos / linux，表示预期运行平台 |
| example | 一条可直接使用的指令 |
| favorite | 可选，true 时放入常用入口 |
| replacement / reason | 弃用时至少填写一个；replacement 为仓库内技能名 |

不要在索引重复名称和描述。修改分类无需移动技能目录。

## 修改后检查

仓库不依赖 npm，也没有自动生成导航或仓库级校验脚本。修改后人工或让 AI 检查：

- SKILL.md 的 name 与目录名一致，description 清楚说明能力和触发场景。
- catalog.yaml 和 README 已同步新增、改名、分类及状态变化。
- 技能引用的参考资料、脚本、模板和示例存在，复制整个技能目录后仍能使用。
- 用一个典型任务验证技能行为，记录实际结果。

Markdown 链接相对所在文件解析；反引号中的资源目录路径相对技能根目录解析。代码示例中的项目路径不是技能资源链接，检查时注意区分。

文件结构检查不能代替技能实际效果、上游 API 正确性或各平台兼容性验证。

## 提交和版本

小改动直接用 Git 提交历史追踪，不为每个技能单独维护版本号。现有技能中的上游版本快照继续保留；它与技能发布版本不是一回事。

建议提交说明：

- feat(daily-report): 支持新的归档方式
- fix(buildadmin-dev): 修正表单约定
- docs(mygo-dev): 更新版本适用范围

整体许可证尚未确定；导入第三方内容时保留来源和许可，不能由仓库许可证覆盖上游权利。
